1 · Current UI (recreated from the render code, 120×32)

Is this an accurate picture of what you have today?

  • Chrome eats the list. Tab box (3) + sub-tab box (3) + now-playing (7) = 13 rows before any content; Search spends 16. On an 80×24 terminal Likes shows 8 tracks.
  • Panes have no focus. Pane 1 moves with ↑↓, pane 2 with Shift+↑↓, pane 3 with Alt+↑↓ (plus the ˚ ∆ macOS fallbacks). Which pane Enter / like / queue acts on is implied by which key you pressed last.
  • Almost everything is Shift+letter and nothing on screen says so. 39 actions, zero hints outside the ? popup.
  • ? is four things: key reference, key editor, settings and equaliser. Themes live somewhere else again (Shift+O).
  • Now-playing bar is 7 rows but says little. No playing/paused/buffering state, no liked state, no up-next; 30% of its width is a decorative sine wave.
  • Lists don't show state. Library tables have no ♥ column and no marker for the playing track; Search has ♥ only.
  • Queue popup is read-only, history is a separate popup, and neither shows where the queue came from.
  • No feedback line. Like, add-to-queue, add-to-playlist and API failures have nowhere to report.
  • Inconsistent placement. Library sub-tabs sit above the list, Search filters below it; the Library filter box pushes the table down 3 rows when opened.

2 · Layout directions

Which skeleton feels right? All four keep your themes, rounded borders and visualiser modes; all four assume a pane-focus model.

A

Tighten

Same bones, half the chrome. Smallest change, lowest risk.

B

Sidebar

Library tree on the left, content in the middle, optional queue on the right.

C

Columns

Ranger-style drill-down. One navigation rule for everything.

D

Player panel

Browser left, permanent now-playing / queue / lyrics panel right.

A · Tighten

Pros

  • 13 rows of chrome → 7; Likes gains 6 rows
  • Every existing screen maps 1:1, so render code is reshuffled not rewritten
  • Hint line teaches the keys

Cons

  • Still tab → sub-tab → pane; Following stays three cramped panes
  • Queue, history, lyrics remain popups / full-screen modes

B · Sidebar

Pros

  • Your playlists are one keypress away from anywhere; no tab/sub-tab hop
  • Track tables always get the wide pane
  • Queue can stay open while browsing

Cons

  • Costs ~26 columns permanently; needs a collapse rule under ~100 cols
  • Largest restructure of state: tab/sub-tab indices become one tree selection

C · Columns

Pros

  • h/l in-out, j/k up-down, everywhere; secondary/tertiary keys disappear
  • Following → artist → tracks/likes stops being three squeezed panes
  • Scales to deeper things later (artist → album → tracks)

Cons

  • Least familiar for a music player; left/right can no longer switch sub-tabs
  • Track columns are narrower while the parent columns are visible

D · Player panel

Pros

  • Cover art, up-next and lyrics/visualiser visible all the time on wide terminals
  • Absorbs the queue and history popups into one place
  • No bottom bar: the list runs to the bottom edge

Cons

  • Needs ≥ ~110 cols to pay off; below that it must fall back to A's bar
  • Multi-pane views (Following) get tight on the left side

3 · QOL picks (independent of layout; pick any)

Which of these would you actually use?

1

Pane focus model

←/→ (h/l) moves focus between panes, ↑↓ always moves the focused one. Retires Secondary/Tertiary keys and the ˚ ∆ fallbacks. Sub-tabs move to [ ].

2

Context hint line

One dim row at the bottom listing the keys that work on the focused thing, read from the live keymap.

3

♥ and ▶ in every list

Liked column and a marker on the playing row in Library, Feed and Search alike.

4

Status / toast line

"Liked", "Added to queue (3)", "Couldn't load playlist: 429" for a few seconds, sharing the hint row.

5

Editable queue + history in one popup

Move, remove, clear, jump-to; History as a second tab of the same popup.

6

Command palette

One key opens a fuzzy list of every action with its binding. Rare actions stop needing a memorised chord.

7

Split Help from Settings

? = read-only key cheat sheet. , = Settings with Keys editor, Options, Equaliser and Themes as its pages.

8

Richer player readout

▶/⏸/buffering state, ♥ for the playing track, up-next title, volume as a bar, source ("from Likes").

9

Unshifted default keys

Normal mode has no text entry, so a queue, f like, s shuffle, r repeat, v visualiser. Old Shift bindings stay as aliases.

10

Jumps

g/G top/bottom, and a key to jump to the playing track in its source list.

11

Sort lists

Cycle sort by title / artist / duration / streams / date added, shown as an arrow in the header.

12

Responsive breakpoints

Under ~100 cols multi-pane views show one pane at a time; under ~24 rows the player collapses to one line.

13

Mini visualiser in the player

Replace the decorative sine with a small live spectrum fed by the same sample buffer.

14

Remember session state

Volume, shuffle, repeat, last tab and visualiser mode restored on start.
